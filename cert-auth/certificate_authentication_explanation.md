# 2. Big picture

The whole certificate flow is:

```text
                    CA
             cert-auth.key
             cert-auth.crt
                  |
                  |
             listens :8080
                  |
                  | CSR
                  v
               SERVER
             server.key
                  |
                  | CSR
                  |-----> CA
                  |       |
                  |       | signs CSR
                  |       v
                  |    server.crt
                  |
                  |
             listens :8081
                  |
                  | server.crt
                  v
               CLIENT
             cert-auth.crt
                  |
                  | validates
                  v
             Continue / Abort
```

The important idea is:

> The CA's private key signs the server certificate. The client already has a trusted copy of the CA certificate and uses the CA's public key to verify that signature.

# 3. `cert-auth.c`

This is the CA program's `main()`.

Its job is:

1. Generate the CA private/public key pair.
2. Create the self-signed CA certificate.
3. Save both to disk.
4. Create a TCP socket.
5. Listen continuously on port `8080`.
6. Accept a connection from the server.
7. Receive the server's CSR.
8. Give the CSR to the certificate-signing function.
9. Send the resulting server certificate back.
10. Close that connection.
11. Go back to `accept()` and wait for another request.

## Important point

The socket creation and infinite server loop are deliberately in `cert-auth.c`.

The cryptographic operations are placed in `services.c`.

So:

```text
cert-auth.c
    |
    +-- networking / main loop
    |
    +-- generate_ca_key()
    |
    +-- generate_ca_certificate()
    |
    +-- save_ca_key()
    |
    +-- save_ca_certificate()
    |
    +-- sign_server_csr()
```

# 4. `services.c`

This file contains the CA's cryptographic functions.

## 4.1 `generate_ca_key()`

```c
EVP_PKEY *generate_ca_key()
```

This creates the CA's RSA key pair.

The function creates an OpenSSL `EVP_PKEY_CTX` configured for RSA:

```c
EVP_PKEY_CTX_new_id(EVP_PKEY_RSA, NULL);
```

Then it requests a 2048-bit RSA key:

```c
EVP_PKEY_CTX_set_rsa_keygen_bits(ctx, 2048);
```

Finally:

```c
EVP_PKEY_keygen(ctx, &key);
```

generates the actual key.

The resulting `EVP_PKEY` contains the RSA private key and corresponding public key.

The private key is extremely important because it must remain with the CA.

The public key will eventually be placed inside the CA certificate.

---

# 5. `generate_ca_certificate()`

```c
X509 *generate_ca_certificate(EVP_PKEY *key)
```

This creates the CA's certificate.

Unlike the server certificate, the CA certificate is self-signed.

That means:

```text
CA private key
      |
      | signs
      v
CA certificate
```

The certificate contains:

- CA identity
- CA public key
- validity period
- issuer
- digital signature

The public key comes from:

```c
X509_set_pubkey(cert, key);
```

The subject is:

```text
C  = IN
O  = NET-SEC-CHAT-APP
CN = NET-SEC-CHAT-APP Root CA
```

Then:

```c
X509_set_issuer_name(cert, name);
```

sets the issuer to the same identity.

This is what makes it self-signed:

```text
Subject = Root CA
Issuer  = Root CA
```

Finally:

```c
X509_sign(cert, key, EVP_sha256());
```

uses the CA's private key to sign the certificate.

---

# 6. Why the CA certificate is self-signed

There is no higher CA in this project.

Therefore, there is nobody else to sign the root CA certificate.

The root CA has to establish trust itself.

So:

```text
CA private key
      |
      v
sign CA certificate
      |
      v
cert-auth.crt
```

The client then receives or already possesses this CA certificate as its trust anchor.

# 7. `save_ca_key()`


This saves the CA private key as:


# 8. `save_ca_certificate()`

```c
void save_ca_certificate(X509 *cert)
```

This saves:

```text
cert-key/cert-auth.crt
```

This is the CA's public certificate.

Unlike the private key, this certificate is intended to be distributed to clients that need to trust this CA.

# 9. `sign_server_csr()`

```c
X509 *sign_server_csr(EVP_PKEY *ca_key, X509 *ca_cert, X509_REQ *csr)
```

This is the most important CA operation.

The server creates a CSR containing:

```text
Server identity
+
Server public key
+
CSR signature made using server private key
```

The CA receives that CSR.

The CA then creates a new X.509 certificate.

The server's subject comes from the CSR:

```c
X509_set_subject_name(cert, X509_REQ_get_subject_name(csr));
```

The issuer comes from the CA:

```c
X509_set_issuer_name(cert, X509_get_subject_name(ca_cert));
```

The server public key is extracted from the CSR:

```c
server_key = X509_REQ_get_pubkey(csr);
```

and placed into the server certificate:

```c
X509_set_pubkey(cert, server_key);
```

Finally, the CA signs the certificate:

```c
X509_sign(cert, ca_key, EVP_sha256());
```

Notice the important distinction:

```text
CSR is signed by SERVER private key.

Certificate is signed by CA private key.
```

That is the central idea of the CA system.

# 11. Server key generation

`generate_server_key()` is very similar to the CA key-generation function.

It creates a 2048-bit RSA key pair.

The resulting key is saved as:

```text
server-key/server.key
```

This is the server's private key.

The server must keep this private.

# 12. Server CSR generation

`generate_server_csr()` creates a Certificate Signing Request.

The CSR contains the server's identity.

Currently the identity is:

```text
C  = IN
O  = NET-SEC-CHAT-APP
CN = localhost
```

The server public key is inserted into the CSR:

```c
X509_REQ_set_pubkey(csr, server_key);
```

Then the CSR itself is signed using the server's private key:

```c
X509_REQ_sign(csr, server_key, EVP_sha256());
```

This proves to the CA that whoever created the CSR possesses the private key corresponding to the public key inside the CSR.

# 13. Server requests a certificate from the CA

The server connects to:

```text
127.0.0.1:8080
```

The protocol is currently very simple:

```text
SERVER                         CA

   |                           |
   |------ CSR length -------->|
   |                           |
   |------ CSR data ---------->|
   |                           |
   |<----- certificate length--|
   |                           |
   |<----- certificate data ---|
   |                           |
```

The CSR is converted to DER before being transmitted.

The CA converts the DER data back into an `X509_REQ`.

The CA signs it and sends the resulting certificate back.

# 18. Why the client does NOT need the CA private key

The client must never have:

```text
cert-auth.key
```

The client only needs:

```text
cert-auth.crt
```

The CA certificate contains the CA's public key.

The client extracts that public key:

```c
X509_get_pubkey(ca_cert);
```

and uses it to verify the server certificate's signature.

The idea is:


# 20. `validate_server_certificate()`

This function currently performs two major checks.

## Check 1 — CA signature

First, the CA public key is extracted:

```c
ca_key = X509_get_pubkey(ca_cert);
```

Then:

```c
X509_verify(server_cert, ca_key);
```

checks whether the server certificate was actually signed by the private key corresponding to the public key in the trusted CA certificate.

If this fails:

```text
Certificate invalid
Connection terminated
```

The client must not continue.

---

# 21. Check 2 — validity period

The client checks:

```c
X509_get0_notBefore(server_cert)
```

and:

```c
X509_get0_notAfter(server_cert)
```

The first check ensures the certificate is not being used before its start date.

The second ensures it has not expired.

So:

```text
notBefore <= current time <= notAfter
```

must be true.

---

# 22. Expected server identity

There is one additional requirement from the assignment:

> The client must verify that the certificate identifies the expected server.

Currently the server CSR contains:

```text
CN = localhost
```

So the client should verify that the received certificate identifies the expected server.

For this single-machine test, the expected identity can be:

```text
localhost
```

When moving to VMs, this should be changed to the actual expected hostname/IP identity used by the deployment.

This is separate from checking the CA signature.

A certificate can be correctly signed by the trusted CA but still belong to the wrong server.

For example:

```text
Trusted CA
    |
    +---- signs ----> server-A certificate
                       CN = server-A
```

If the client expects `server-B`, it must reject that certificate even though the CA signature is valid.

# 25. Difference between keys and certificates

It is important not to confuse these.

## CA private key

```text
cert-auth.key
```

Secret.

Used by CA to sign certificates.

## CA certificate

```text
cert-auth.crt
```

Public/trusted.

Contains CA public key and CA identity.

Used by clients to verify certificates signed by the CA.

## Server private key

```text
server.key
```

Secret.

Used by the server for operations proving possession of its private key.

## Server certificate

```text
server.crt
```

Public.

Contains server public key and server identity.

It is signed by the CA.

# 26. Important distinction: certificate validation vs private-key possession

The current certificate validation proves:

```text
"The certificate was signed by my trusted CA."
```

It does NOT by itself prove:

```text
"The machine sending me this certificate actually possesses the corresponding private key."
```

This is why the assignment has the additional requirement:

> The server must prove that it possesses the private key corresponding to its certificate.

The next step is therefore to add a challenge/signature mechanism.

---

# 27. Server private-key proof

A simple mechanism is:

```text
CLIENT                         SERVER

   |                              |
   |---- random challenge ------->|
   |                              |
   |                              | sign challenge
   |                              | using server.key
   |                              |
   |<---- signature --------------|
   |                              |
   | verify signature using       |
   | public key from server.crt   |
   |                              |
```

The client obtains the server's public key from:

```text
server.crt
```

The server signs the challenge using:

```text
server.key
```

If the signature verifies, the client knows that the server possesses the corresponding private key.

This is stronger than simply receiving a certificate file.

---

# 28. Why an attacker cannot simply copy the certificate

Suppose an attacker obtains:

```text
server.crt
```

They can send that certificate to the client.

But they do not have:

```text
server.key
```

Therefore they cannot correctly sign the client's fresh challenge.

The client detects this because signature verification fails.

So:

```text
Certificate alone
       |
       X
       |
Not enough
```

whereas:

```text
Certificate
+
Correct private-key signature
       |
       v
Server proves possession of private key
```

# 29. Full intended protocol

Once the private-key proof is added, the connection should look approximately like this:

```text
CLIENT                              SERVER

   |                                   |
   |---------- TCP connect ----------->|
   |                                   |
   |<--------- server certificate -----|
   |                                   |
   | validate CA signature             |
   | validate validity                 |
   | validate expected identity        |
   |                                   |
   |------ random challenge ---------->|
   |                                   |
   |                                   | sign challenge
   |                                   | with server.key
   |                                   |
   |<--------- signature --------------|
   |                                   |
   | verify using public key           |
   | from server certificate           |
   |                                   |
   |------ continue protocol --------->|
   |                                   |
   |              DH                   |
   |<--------------------------------->|
   |                                   |
   |          authentication           |
   |<--------------------------------->|
   |                                   |
   |             chat                  |
   |<--------------------------------->|
```

The important ordering is:

```text
Certificate
    ↓
Certificate validation
    ↓
Server private-key proof
    ↓
DH
    ↓
Password/authentication
    ↓
Chat
```

If certificate validation fails, everything after it must stop.

If private-key proof fails, everything after it must also stop.

# 32. The most important concepts to remember

### CA

A trusted authority that signs certificates.

### Root certificate

The CA's self-signed certificate containing its public key.

### CSR

A request from the server asking the CA to certify its public key and identity.

### Server certificate

The CA-signed document binding the server identity to the server public key.

### Certificate signature

Proof that the trusted CA approved the certificate.

### Private-key proof

Proof that the server actually possesses the private key corresponding to the public key in the certificate.

### Trust anchor

The CA certificate that the client already trusts.

### Certificate validation

The client checks:

```text
CA signature
+
validity period
+
expected server identity
```

before proceeding.
